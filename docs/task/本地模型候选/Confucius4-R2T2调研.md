# Confucius4-R2T2 调研（2026-11-14，暂不接入）

模型页：<https://huggingface.co/netease-youdao/Confucius4-R2T2>，论文 arXiv 2611.06043。

## 它是什么

- 网易有道基于 Qwen3-ASR-1.7B 微调的流式识别模型：音频编码器和投影层冻结，只用约 1500 小时中英文数据（SFT + GRPO）训练文字解码器，结构不变。
- 「快」指延迟低，不是吞吐高：音频每 80 ms～2 s 一块，已输出的字不再修改（Longest Stable Prefix），拿不准的末尾几个 token 暂缓输出；`unfixed_token_num` 控制暂缓几个。整段识别的计算量与原版千问相同。
- 官方数据（160 ms 一块、暂缓 1 个 token）：错误率 5.76%，原版千问同设置 21.01%，原版整段识别 5.15%。中英文以外语言上整段准确率可能不如原版。
- 发布内容只有 safetensors（约 4 GB），官方推理走 vLLM（Python + NVIDIA 显卡），另有可选的 llama.cpp 解码。没有 transcribe.cpp 可用的 GGUF。
- 权重许可是网易自有的模型使用协议（据报道月活过亿需另行商用授权），代码 Apache 2.0；转存到我们的 ModelScope 仓库分发前要核对条款。

## 对我们的价值

本地千问现在做实时听写和字幕是「VAD 切句 + 说话中隔段整句重识别做预览 + 句末再识别」：预览会跳字，长句重算越来越慢。R2T2 的只增不改、增量解码正好解决这两点，价值在实时听写和实时字幕；对整段转写没有提速。

## 为什么暂不接

1. transcribe.cpp 没有这种分块接着解码、带已确认前缀续写的接口；要真正流式就得自己改引擎或等上游支持。
2. 只转成 GGUF 按整句用（结构相同，大概率能用 transcribe.cpp 的 qwen3_asr 转换脚本）没有速度收益，准确率还可能略低于原版。
3. 1.7B 每 160 ms 推理一次，只有处理器的电脑扛不住。

## 以后要试时的步骤

1. 核对许可后下载权重，用 transcribe.cpp 的转换脚本转 GGUF，按整句跑我们的中文样本，对比原版千问的准确率与耗时。
2. 结果不差，再评估自己实现分块流式解码，或等 transcribe.cpp 原生支持。
