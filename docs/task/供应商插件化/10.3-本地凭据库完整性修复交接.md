# 10.3 本地凭据库完整性修复交接

## 结论

10.2 发现的 6 组问题已从宿主契约、键空间、持久化事务和跨进程 IO 四个层面完成根因修复。生产路径仍为应用自管的 AES-256-GCM local vault，没有重新引入 Keychain、Credential Manager、DPAPI 或 `keyring`，本任务没有读取真实凭据、发起网络请求或执行付费调用。

## 宿主可信的 secret 契约

- 插件清单的 `secret` 布尔值不再是安全边界。宿主会把 `authKind=api-key` 的 `apiKey`、`fieldType=password`，以及 `apiKey`、`clientSecret`、`*Token`、`*Secret`、`*Password` 等已知敏感名称强制视为 secret。
- 配置更新、schema v4 持久化拒绝、v2 迁移清理、WebView `sanitizedConfig` 和 QuickJS 插件运行时的 `secretFields` 统一消费宿主判定；恶意插件不能通过 `secret=false` 把值写回普通配置或前端快照。
- 断牙测试覆盖 `authKind=api-key`、伪装为 text 的 `clientSecret`、伪装为非 secret 的 password 字段，以及 WebView 输出与插件运行时读取边界。

## 不相交 CredentialKey

`CredentialKey` 内部改为三种结构化 owner：

- `Provider { providerId }`
- `Plugin { pluginId, providerId }`
- `PluginSession { pluginId }`

落库账号带 `credential:v1` 与不相交类型标签；所有组件禁止冒号和控制字符，因此编码可逆且不能跨类型碰撞。`pluginId=session + providerId=victim + field=browserSession` 已有回归测试证明不能再与 `victim` 的插件会话相撞。

旧的 provider 和普通插件凭据账号仅在无歧义时只读回退，后续写入使用新账号；旧 `plugin-session:*` 与 `pluginId=session` 的账号因历史格式本身有歧义，不做猜测迁移，相关网页登录会话需要重新登录。

## vault 完整性与跨进程并发

- 新增 `fs2` 文件锁，跨进程独占锁覆盖主密钥创建以及 vault 的完整 read-modify-write；进程内 Mutex 仍用于避免同进程线程争用。
- `CredentialStoreHandle::write_verified` 对正式 local vault 使用同一把锁完成“旧值快照 → 写入 → 回读 → 必要时恢复”，不再由三个可交错的独立调用拼接事务。
- `master.key` 在最终路径使用 `create_new`，不再通过 Unix `rename` 覆盖竞争者。若首次创建在 32 字节写完前中断，且 vault/备份均不存在，会安全清理残缺文件并重试；一旦已有 vault 或备份则明确拒绝重新生成。
- vault 主文件缺失时会验证备份的 AEAD，再原子恢复；恢复失败会显式返回并保留备份，绝不返回空库。主文件损坏只接受认证通过的备份；IO 错误和“不支持版本/算法”不会触发降级恢复。
- 写入先把旧主文件原子提交为备份，再原子替换新主文件。Unix 使用同目录 rename 并 fsync 父目录；Windows 使用 `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`，取消旧的 remove→rename 窗口。
- 8 个独立测试进程从空目录并发创建、写入同一个 vault，验证只产生一把 32 字节主密钥且 8 项更新无丢失。

## schema v2→v4 崩溃一致事务

迁移使用 `Prepared → Committed / RolledBack` 事务标记，并保存迁移前主配置与备份的私有快照：

1. 主配置和备份快照先写入、刷盘；`Prepared` 标记提交后才允许替换正式文件。
2. vault 写入回读通过后，先原子提交无明文 backup，再提交无明文 primary，最后把标记持久化为 `Committed`。
3. 任一正式替换失败，先从快照恢复 primary 与 backup 并标记 `RolledBack`，确认目录持久化后才回滚 vault。
4. 启动发现 `Prepared` 会恢复旧配置并重试；发现 `Committed` 只清理快照，不会恢复旧明文；无 marker 的孤儿快照会清理。
5. schema v4 启动时会修复缺失、损坏、旧 schema 或仍含明文的 backup；主配置缺失或损坏时，只有合法备份能原子恢复。
6. 整段 v2→v4 迁移另有状态文件级 `fs2` 跨进程锁；回滚前还会确认 vault 当前值仍是本事务写入值，不会删除并发方后来更新的凭据。

常规状态保存也统一复用同一套原子替换：先将旧主配置写入并刷盘到 backup，再原子替换 primary。Windows 不再执行“删除 primary → rename”的有缺口协议。

故障注入覆盖最终 primary 替换失败、备份恢复失败、`Prepared` 崩溃点、`Committed` 清理崩溃点、旧明文 backup 清理和不支持新 vault 版本不降级。

## 残余安全边界

- master key 与 vault 仍由同一操作系统用户的私有 Local App Data 权限保护，不能抵抗已控制该用户账户或已注入 Say-It 进程的攻击者。
- `fs2` 是协作式文件锁；Say-It 的所有正式 vault 访问均遵守该锁，但无法阻止同权限恶意进程绕过协议直接改文件。AEAD 会检测密文篡改。
- Windows 继续继承当前用户 Local App Data ACL；本任务没有引入 DPAPI，也没有额外创建系统授权弹框。
- 历史歧义插件会话不自动猜测归属，升级后需重新登录；内置 provider 与非 `session` 插件凭据可继续通过无歧义旧账号读取。
