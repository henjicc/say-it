# 9.16 凭据与 ID 一次性迁移交接

## 结论

- `say-it-state.json` schema 由 **2 升为 3**。schema v2 启动时执行一次性迁移；成功后运行时不再保留 `funasr` provider alias 或旧 kind 分支。
- 在线供应商 API Key 与 `configFields.secret` 字段统一进入 `CredentialStore`。macOS 使用 Keychain，Windows 使用 Credential Manager；Linux 当前构建没有安全后端，遇到在线密钥会明确阻止迁移/写入，不回退明文文件。
- WebView 只获得 `hasApiKey/configured` 状态。已删除 `get_provider_api_key` Tauri 命令和两个设置页的已存密钥显隐入口；`SecretInput` 只能显示当前尚未保存的草稿。
- QuickJS 初始化前对 profile config 再做一次 `sanitized_config`；SDK RuntimeContext 只能在 Rust 预绑定的 `providerId + scope + CredentialKey` 范围内读取凭据。
- 删除自定义 LLM 供应商或卸载插件只删除 profile/包，**不删除系统凭据**。这是恢复/重装语义；未来若产品需要“忘记凭据”，应新增显式动作，不能挂在卸载上。

## 统一 CredentialStore

入口：`src-tauri/src/providers/credential_store.rs`。

```text
service = com.henjicc.sayit.credentials

内置/普通供应商 account = provider:{providerId}:{fieldKey}
插件 account            = plugin-{pluginId}:{providerId}:{fieldKey}
```

关键契约：

1. `CredentialStore` 只有 `get/set/delete` 三个领域动作，测试可注入 fake store。
2. `CredentialStoreHandle::write_verified` 写入后立即回读；校验失败会恢复旧值或删除本轮新值。
3. `key_for_profile` 根据 `plugin:<pluginId>` 自动使用插件命名空间，避免不同插件复用 provider/field 时串密钥。
4. `RuntimeState.credentials` 是宿主唯一凭据入口。
5. 旧 Rust 执行链通过 `provider_profile_for_execution` 在一次调用前构造短生命周期 profile；插件/model-pack profile永不回灌 secret。9.13 切到 SDK 执行层后可删除这段旧执行适配，不要再建第二套存储。

## schema v3 迁移顺序与失败语义

迁移位于 `src-tauri/src/persistence.rs`：

1. 从可用主文件或备份反序列化 schema v2。
2. 扫描内置百炼、所有 `llm:*`、`authKind=api-key`、插件显式 `configFields.secret=true` 字段。
3. 计算目标身份后写入系统凭据库；`funasr` 的 Key 直接写到 `provider:bailian:apiKey`。
4. 每项立即回读比对；已有相同值视为幂等成功，已有不同值则拒绝覆盖。
5. 任一失败时逆序恢复本轮改动，schema 不升级，主配置与备份原文保留，错误文本执行 secret 脱敏；下次启动自动重试。
6. 全部凭据验证成功后，执行 ID 改写：
   - `profiles[].id: funasr -> bailian`
   - `profiles[].kind: alibabacloud-funasr -> sdk:bailian`
   - `defaults.asr/translation: funasr -> bailian`
   - `defaults.llm: funasr -> llm-groq`
   - `dictationPrefs.smartLlmProviderId` 与 assistant 各 feature 的 `llmProviderId`: `funasr -> llm-groq`
7. 删除所有 secret 字段，schema 置为 3。
8. 用**同一份脱敏字节**先原子替换 `.json.bak`，再替换主文件。成功后主文件和备份都不含密钥或旧 provider ID。

schema v3 的常规保存会先执行 `ensure_no_plaintext_credentials`；只要 profile config 出现 secret 字段或废弃 provider ID，就拒绝序列化，避免未来回归为明文存储。

## 其他持久化 ID

- `shared/asr-models.json` 的 9 个在线模型统一改为 `providerId: bailian`；模型 ID 与 Fun-ASR 协议族名称不变。
- 历史 SQLite 初始化时幂等执行 `history_entries.provider_id = funasr -> bailian`。这是历史展示字段，不改 modelId。
- 审计确认 ASR/字幕/文件转写的持久化选择保存的是 modelId，不需要改名。

## 宿主与插件安全边界

- `SdkHostBindings.provider_id` 与 `credential_scopes` 先做权限判断，随后只读取预绑定的 `credential_key`；QuickJS 不能提交任意 account。
- 百炼 SDK 绑定使用 `provider_id=bailian`、`CredentialKey::provider("bailian", "apiKey")`。
- Groq SDK 的正式 provider ID 是 `groq`，Say-It 当前配置 profile ID 是 `llm-groq`；9.13 应绑定 `provider_id=groq`，但凭据键使用 `CredentialKey::provider("llm-groq", "apiKey")`。两者刻意分离，不要新增 `groq/llm-groq` alias 分支。
- 插件 SDK 绑定使用 `CredentialKey::plugin(plugin_id, provider_id, field_key)`，并只授予 manifest capability 对应 scope。
- v3/v4 插件不会再从 `initialize(request.config)` 获得 secret；后续 v5 插件必须通过 SDK RuntimeContext 读取。没有为旧插件保留双路 secret 兼容层。

## 9.13 输入与剩余边界

1. 9.13 直接复用 `RuntimeState.credentials`、`CredentialKey` 和现有 `SdkHostBindings`，不得在 SDK adapter、插件 runtime 或 WebView 另建 secret cache。
2. SDK 业务路由切换后，删除旧 Rust 供应商执行实现及 `provider_profile_for_execution` 的临时原生执行适配；Apple/Sherpa 本地链路不动。
3. SDK descriptor/provider 只注册 `bailian`、`groq`；不得重新引入 `funasr` alias。旧 Fun-ASR 字样只允许作为模型族/协议路由名称。
4. 插件 v5 创建 bindings 时必须从插件 manifest 的 provider/source namespace 计算 `CredentialKey::plugin`，不能让插件传 account 字符串。
5. Linux 若要支持在线供应商，必须先选择有维护的 Secret Service 后端并补真机测试；禁止用环境变量、JSON 或自建加密文件静默降级。
6. 当前没有“清除已存 API Key”产品动作；9.13 不应借卸载顺便删除。若后续新增，需显式确认、单独审计和 fake store 删除测试。
