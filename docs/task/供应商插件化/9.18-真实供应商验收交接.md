# 9.18 真实供应商最小付费验收交接

> 10.1 已把正式链路切换为本地加密 vault，不再读取或删除 Keychain/Credential Manager 条目。下列供应商结果是切换前的历史实测证据；当前再次执行 live harness 前，必须在 Say-It 中重新填写凭据。harness 现会定位应用私有目录的 local vault，不再触发系统凭据授权框。

## 结论

本轮已建立可重复、默认禁用的正式 live harness，并按授权实际执行矩阵。验收没有得到供应商成功响应：Say-It 当前系统凭据状态使所有请求都在网络前终止，因此实际可计费请求为 **0**。

- 百炼：`provider:bailian:apiKey` 在当前 macOS Keychain 中不存在；7 个代表项均在 46～76 ms 内返回 `missing_credential`，无 HTTP/WS、无上传、无轮询、无事件。
- Groq：`provider:llm-groq:apiKey` 的 Keychain 项元数据存在，但测试进程读取值时系统调用不返回。生产宿主根因修复后只再尝试一次，10,046 ms 受控返回 `timeout`，未进入模型发现网络请求；按约不再重试。
- 取消：在不读取凭据、不发网络的前置取消场景中 46 ms 返回 `cancelled`，HTTP stream、WS、span/timer 资源均为 0。
- 日志：内存结构化 recorder 检查未出现 `Authorization`、Bearer、API Key 字段名或 Base64 载荷标识；live 输出仅有模型/协议/状态/耗时/事件类型/数字 usage/不可逆摘要。

这不是供应商 API、额度或模型协议失败；当前阻塞发生在正式 CredentialStore 边界。没有从其他应用复制密钥，也没有读取、输出、写文件或提交任何真实凭据。

## 发现并修复的真实缺陷

### 历史系统凭据同步读取可无限阻塞

初次矩阵执行已推进过全部百炼项，但 Groq 在 `HostState::credential_get → keyring get_password` 阻塞约 10 分钟。SDK 的 45 秒 timeout 无法打断同步系统调用。

根因修复：

- 生产 `credential.get` 与 `plugin.credential.get` 统一进入固定 4 个 worker、16 项有界队列；
- QuickJS 线程只等待当前宿主 deadline，且单次凭据读取最多 10 秒；
- 取消在入队前和等待期间检查；
- 超时只返回脱敏错误，QuickJS 调用继续收尾，网络/WS/span/timer 资源释放；
- 若系统调用自身迟迟不返回，最多占用固定 worker，不再无限阻塞 QuickJS 或无界创建线程。

`bounds_blocking_credential_store_by_host_deadline` 使用会阻塞 250 ms 的 fake store 与 50 ms 宿主 deadline，约 0.13 秒内受控失败并证明资源 `(0,0,0)`。

### harness ASR source 名称

首版 harness 错把 SDK connector source 写为 `speech-recognition`，而正式 connector 唯一 source 是 `asr`。这只影响新 harness，没有影响应用生产路由。已改为 `source=asr` + module ID `bailian.speech-recognition.<model>`，并新增无密钥 fixture 精确证明会进入正式 SDK 模块并返回 `api_key_missing`。

## 凭据迁移只读审计

只检查字段是否存在/非空与 Keychain 项元数据，不读取值、长度或哈希：

- 主配置与备份均为 schema v3；
- 主/备份均无 `funasr` provider/default；
- 主/备份所有 profile 的 `config.apiKey` 字段均“不存在且非空=false”；
- 当前与历史应用数据目录都没有可用的 schema v2 明文来源；
- Keychain service 与生产代码一致：`com.henjicc.sayit.credentials`；
- 百炼目标 account `provider:bailian:apiKey` 不存在，历史 account `provider:funasr:apiKey` 也不存在；
- Groq 目标 account `provider:llm-groq:apiKey` 元数据存在；
- 应用数据目录没有迁移日志文件可供追溯。

迁移实现只有在所有旧明文凭据写入并回读成功后才升级 schema v3，失败会保留原文并回滚；现状不支持“迁移丢失/命名错配”的判断。可得出的最窄结论是：百炼在 Say-It 可审计配置中从未留下待迁移明文，或其系统凭据后来被外部删除；没有证据表明 9.16 迁移丢失了密钥。
