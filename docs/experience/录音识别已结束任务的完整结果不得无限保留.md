# 录音识别已结束任务的完整结果不得无限保留

## 根因和消费者

TranscriptionRuntime 原先用两个 HashMap 无限保留每个任务的最后完整结果和用途。窗口销毁只能释放前端副本，Rust 中的文本、句子与时间戳仍随任务次数增长。恢复窗口又克隆并序列化全部任务，实际前端只为字幕转写与文稿对齐各选择一个任务。

模型对比与 file 模式听写通过 BackendEvent::Transcription 的独立载荷消费结果，分别更新自己的领域状态；它们不从转写窗口恢复接口读取完成结果。此次清理只针对多余的临时运行时投影，不修改历史数据库、导出文件、识别结果内容、对比结果或听写处理逻辑。

## 保留规则

- 所有运行中任务继续保留状态。字幕转写与文稿对齐各保留最近登记的任务结果；新任务开始后，旧的已结束恢复副本可释放。旧任务若仍运行则继续保留，到结束时不覆盖更新任务的恢复结果。
- 听写与模型对比的终态事件仍完整发送给 Rust 与前端订阅方，但不再在通用转写投影里长期复制保存其载荷。
- 任务用途登记只在实际工作退出后清理。设置取消标记或发出取消事件不等于工作已退出；期间再次收到事件仍要保留正确用途。
- 未登记或已注销任务的迟到事件不再重新建立投影，防止旧取消被误归到字幕转写并使缓存复活。所有生产任务均在发送事件前显式登记；未知用途仍按原约定归为字幕转写。
- 任务序号在同一把投影锁内分配，恢复列表按登记顺序排列。UUID 的字典顺序不代表任务新旧。前端仍优先选择运行任务，并在同类任务中选择最新登记的一项。

保留上界是运行中任务加最多两个页面恢复结果，不是把完整结果截断到固定字节数。并发运行中的合法任务仍占用各自资源；单个最新长结果也仍需完整保留。

## 验证

领域回归连续完成四种用途各 1,000 个任务后，只剩两个页面的最新结果，用途登记表为空；覆盖旧任务晚完成、新任务失败、取消到实际退出的间隔、退出后迟到事件和结果用途。前端六项窗口恢复测试覆盖按后端登记顺序选择最新任务、运行任务优先以及用途隔离。完整 Rust release 回归 665 项通过、24 项显式忽略、0 项失败，TypeScript 类型检查通过。

Windows release，256 份约 480 KiB 的合成文本结果，四种用途轮换，每组三个独立进程取中位数：

| 指标 | 冻结旧保留方式 | 新保留方式 |
| --- | ---: | ---: |
| 最终保留任务数 | 256 | 2 |
| 最终私有提交 | 125.973 MiB | 5.078 MiB |
| 峰值私有提交 | 125.973 MiB | 5.543 MiB |
| 处理耗时 | 75.609 ms | 108.060 ms |
| 完整发送文本字节数 | 125,831,168 | 125,831,168 |

旧组冻结原先的完整结果表和用途表，新组调用实际投影代码。新组包含任务处理期间的释放成本，旧组把旧结果保留到测量结束；约 32ms 的批次耗时增加不能忽略，但也不能外推为真实识别速度下降。峰值私有提交下降约 95.6%，不代表整应用同等降幅。此测试没有网络、模型、磁盘迁移或工作集强制修剪，也没有测试物理窗口开关与 macOS 实机。

可重复入口为 scripts/measure-audio-performance.mjs 的 transcription-retention / transcription-retention-legacy。原始 JSON 位于工作区/performance/transcription-retention[-legacy].json，含程序 SHA256；功能回归独立检查具体内容与用途，基准额外检查完整文本字节数。
