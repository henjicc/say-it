# 窗口反复销毁验收必须同时跟踪子进程和主进程句柄

## 验收边界

只看到 WebView2 子进程退出，不足以证明主进程没有累积资源。使用 `performance-acceptance` 可选特性构建真实 Tauri 应用，自动重复主窗口打开、前端 ready 握手、CloseRequested、销毁和闲置流程。普通发布版不包含此入口。

验收构建强制要求 identifier 为 `com.henjicc.sayit.acceptance`，并拒绝该数据目录中的重定向和重置标记。测试使用独立默认数据，不访问正式设置或调用识别服务。后续排查发现首次使用向导会自动打开麦克风验证设备，因此验收构建在内存中跳过向导；这不改变正式设置。不能将独立默认配置的窗口占用直接与用户已配置版本比较。

构建时将下列 JSON 保存在忽略目录，再给 `npm run tauri:build -- --no-bundle --features performance-acceptance --config <配置路径>`：

```json
{"identifier":"com.henjicc.sayit.acceptance","productName":"SayIt Acceptance","mainBinaryName":"SayItAcceptance"}
```

使用 `scripts/measure-app-lifecycle.ps1 -Executable <验收程序> -OutputDirectory <每轮新目录>` 启动并采样。程序执行 10 次开关后自动退出；输出阶段事件与完整进程采样。随后用 `node scripts/summarize-app-lifecycle.mjs <输出目录>` 提取各阶段末尾的稳定值。当前验收构建强制冷启动到托盘，初始 idle 没有加载主窗口；早期两轮结果是在 setup 后主动销毁窗口，不能混作同一基线。

采样器记录实际间隔，跟踪曾确认的子进程直到它真正退出，即使其父进程先退出；同时记录应用退出两秒后仍存活的已知进程。CPU 差分只比较同一 PID 与启动时间，进程集合变化的区间标为不可比较。私有字节表示提交量；工作集求和可能重复计算共享页。约一秒采样不能代表瞬时峰值。

## 2026-09-24 初次结果

基于 `11c5bdd` 的两次独立验收进程，各执行 10 轮：

- 20 次窗口打开、就绪与关闭均成功；打开到 ready 约 1.55～2.24 秒，关闭到窗口消失约 26～52 毫秒。
- 每次关闭等待约五秒后，整组进程都回落到单个主进程。第二轮应用退出两秒后没有已知残留进程。
- 第一轮关闭后的主进程从 12.13 MiB、420 句柄增长到 14.94 MiB、483 句柄。
- 第二轮从 12.07 MiB、412 句柄增长到 14.30 MiB、485 句柄；最终额外闲置 20 秒后仍为 14.27 MiB、483 句柄。
- 阶段末尾约一秒的 CPU 采样中，关闭状态均未测得增量；这不等于整段时间绝无 CPU 活动。

原始记录位于忽略目录 `工作区/performance/window-lifecycle-{1,2}/`，其中有验收二进制 SHA256。这些结果证明子进程回收有效，但主进程存在可复现的句柄增长，不能宣称窗口生命周期整体验收通过。需继续识别增长资源及归属；尚不能据此判定 Tauri/WebView2 或应用代码是根因，也不能把全部内存差值认定为泄漏。

## 分离自动采集与输入法影响

- 去掉首次向导的自动采集后，完整 UI 仍然出现每轮约 8 个句柄增长，说明自动采集不是该增长的必要条件。
- 独立进程中执行 12 次真实麦克风短时启动/释放：预热后句柄保持 213，采集 worker、原始音频接收者和待处理包均清空。另一个进程执行 12 次设备枚举，句柄始终为 213。两项诊断均为默认忽略测试；采集测试还要求显式设置 `SAYIT_ALLOW_MIC_LIFECYCLE=1`，不保存、不发送音频。不能仅凭 CPAL 的实现细节推断它泄漏并修改停止逻辑。
- 对完整 UI 的主进程做内核句柄快照，每轮增加两个指向 `TENCENT/WeType` 及其 `crash` 目录的文件句柄，并增加六个事件句柄。句柄读取有竞争，标为 unavailable 的项不能当作资源已经释放。
- `-BlankWebview` 可跳过 React，只创建空白 WebView；其可见耗时不等于正常 UI ready 耗时。空白对照后期句柄稳定，但部分浏览器后台子进程退出晚于五秒，所以必须继续跟踪它们，不能只检查当前父子关系。
- `-DisableTestIme` 仅在验收构建创建窗口前调用 `ImmDisableIME(u32::MAX)`，用于输入法的因果对照，不改变系统输入法设置，也不能作为正式版本的性能修复。该轮后半段关闭后句柄稳定在 353，最终 352；私有提交约 11.2～12.0 MiB 波动，最终 11.66 MiB。应用退出两秒后无已知子进程残留。

- 用同一二进制恢复输入法再次执行 10 轮（`window-ime-control-1`），关闭后句柄又从 404 增长至 477，额外闲置后 476；私有提交最终 13.90 MiB。与仅禁用验收进程 IME 的结果形成因果对照。正式版本保留中文输入，不手动关闭第三方句柄，也不为这项约 2 MiB 的本次末态差值引入高风险进程重构；长时间累积的外部问题仍作为已知限制。

新记录在 `window-no-onboarding-1`、`window-handles-diagnosis`、`window-no-ime-1` 和 `window-ime-control-1`。这些数据用于定位资源归属，不代表识别业务已经完成应用级验收。

## 使用同一采样器验证业务生命周期

`-Scenario subtitle-preview` 使用实际字幕预览命令和原生指示窗口，固定文本循环五轮，不启动识别、音频采集、翻译服务或 OBS 输出。每轮检查预览已激活且没有识别会话，停止后检查指示窗所有权释放。`-Scenario audio-lab` 验证长素材离线处理，具体边界见音频调校经验文件。两个场景均保留普通输入法行为，不使用 `-DisableTestIme`。

2026-09-24 的 `subtitle-preview-app-1`：冷启动私有提交 6.57 MiB；五轮预览观测最高 14.68 MiB，最后闲置 13.77 MiB。首次预览之后句柄始终为 268；停止和最终闲置的有效 CPU 采样没有测得增量。活动阶段平均 CPU 约 0.14%～0.23%（按本机全部逻辑处理器归一化）。开启命令约 0.93～1.12 ms、关闭约 0.06～0.09 ms，表示命令完成，不是屏幕首帧延迟。整段仅一个应用进程，退出后无已知残留。首次显示后的字体/绘制初始化等驻留成本没有随这五轮继续累积，不能据此断言更长时间完全不会增长。

汇总器同时输出稳定阶段末值与各阶段观测峰值、有效 CPU 差分覆盖时长。短于采样间隔的工作可能漏掉；长音频校验哈希产生额外读取，因此 `audio-processing` 阶段采样还包含校验过程，命令计时则不含哈希读取。上述验证不覆盖鼠标交互、实际屏幕字形、识别质量和外部服务链路。

本阶段验收构建成功，两个新增场景完成；默认特性的完整 Rust release 回归为 715 项通过、32 项显式忽略、0 项失败。普通构建不包含场景入口或音频注入方法。

## 自动空闲回收接入后的最终复测

2026-09-25，`工作区/performance/window-auto-reclaim-final` 使用 SHA256 `AF76B5DDE9B73F5FB6C5B24BA82A0755B93AB9513FF2EFB4688032EF2DB2B84F` 完成十次正式主窗口打开/关闭，保留普通输入法，没有手动堆回收或工作集修剪。初始私有提交 6.66 MiB；最后额外闲置二十秒后为 12.79 MiB、29 线程、478 句柄，仅主进程，CPU 最后采样区间未测得增量。自动空闲回收执行十次，退出后无残留子进程。

前面三次关闭五秒后仍分别有 3、5、7 个已确认的应用进程，后来均退出；后七次关闭后为一个主进程。不能把“窗口消失约 25～27 ms”等同于全部浏览器资源立即释放。打开阶段末私有提交合计约 346～452 MiB，其中主进程约 25～29 MiB；前几轮还包含延迟退出的浏览器进程。该数字来自应用私有提交之和，不是去重物理内存，也不能把不同轮次当作同条件优化对照。打开到可见约 1.11～1.49 秒。

主进程句柄仍呈此前已定位的输入法相关增长：第四轮关闭后 432，第十轮 479，最终 478。自动堆回收不负责关闭第三方输入法句柄，故该外部限制仍然存在，不能宣称所有增长均已消除。要显著降低主界面打开时的总体占用，主要成本已经在 WebView 进程组；继续只优化 Rust 闲置堆的收益有限。
