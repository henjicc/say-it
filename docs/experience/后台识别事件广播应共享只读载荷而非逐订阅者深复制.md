# 后台识别事件广播应共享只读载荷而非逐订阅者深复制

## 根因

BackendEventHub 原先广播可深复制的 BackendEvent，内含完整 serde_json::Value 或翻译文本。Tokio broadcast 为每个接收者取得事件副本，导致听写、字幕、模型对比即使随后按会话 ID 忽略某条结果，也先支付了完整载荷复制成本。实时识别的生产者还在入队前额外 clone 了一次不会再使用的 Value。

## 实现与边界

- 通道保存 Arc<BackendEvent>，三个消费者借用事件字段；只为自己的长期业务状态提取并保存必要内容。识别生产者将载荷直接移入事件。
- 不把 Value 换成可变共享对象，不引入额外锁，也不改变事件内容、顺序、会话匹配、队列容量或落后处理规则。字幕译文只在所属会话有效时复制到字幕状态中。
- 生产编译下 BackendEvent 不再实现 Clone，防止后续无意恢复深复制；测试编译仅为冻结旧通道的对照测量保留 Clone。
- 发布者克隆返回同一个受控发布接口，不能绕过共享事件包装。
- 载荷在最后一个接收者用完后释放。慢接收者持有期间仍占用一份完整载荷；引用共享不等于队列没有内存成本，也不解决订阅者执行过慢或业务队列积压本身。

## 验证

完整 Rust release 回归 668 项通过、25 项显式忽略、0 项失败。新增回归验证三个接收者指向同一完整对象、文本和时间戳内容不变、最后一份引用释放后 Weak 无法升级、慢订阅者退出清理未读载荷，以及超过原有 256 条容量时仍明确返回 Lagged 并释放被覆盖对象。

Windows release，每组三个独立进程取中位数。使用三个实际 broadcast 接收者，每批 64 条事件，收到后共同持有这一批，再释放。大载荷场景共 64 条、每条文本 256 KiB；小载荷场景共 4,096 条、每条文本 128 字节。旧组冻结 Sender<BackendEvent>，新组走实际 BackendEventHub。所有接收者逐条核对序号、final 标记和文本长度。

| 场景 | 旧峰值私有提交 | 新峰值私有提交 | 旧耗时 | 新耗时 |
| --- | ---: | ---: | ---: | ---: |
| 大载荷广播 | 52.863 MiB | 20.281 MiB | 27.620 ms | 9.204 ms |
| 小载荷广播 | 3.945 MiB | 3.734 MiB | 12.161 ms | 4.842 ms |

大载荷峰值下降约 61.6%，批次耗时下降约 66.7%；小载荷批次耗时下降约 60.2%。三个接收者累计读取文本字节数分别为 50,331,648 和 1,572,864，新旧一致。该测试含构造载荷、广播、检查与释放成本，不含网络、识别模型、界面或整个应用；不能外推为实际识别速度、整应用 CPU 或内存同等降幅。未进行 macOS 实机验证。

可重复入口为 scripts/measure-audio-performance.mjs 的 event-fanout[-legacy] 和 event-small-fanout[-legacy]。原始 JSON 在工作区/performance/ 同名文件中，包含程序 SHA256。
