# macOS 全局鼠标释放事件与按钮状态不同步

## 现象

`CGEventTap` 能收到 `kCGEventLeftMouseUp`，但基于 `CGEventSourceButtonState` 组装的 `buttonDown` 仍可能是 `true`。如果识别器先判断持续按下状态，再判断释放沿，完整点击会被当作仍在按住，导致鼠标和触控板连击都无法成立。

## 处理原则

- 点击状态机应优先处理事件自身携带的 `leftPressed` / `leftReleased` 边沿，再参考全局按钮状态处理拖拽。
- macOS 原生回调应以当前 `mouseDown` / `mouseUp` 事件修正 `CGEventSourceButtonState` 的滞后一拍结果。
- 连击次数优先使用 `kCGMouseEventClickState`，它同时覆盖外接鼠标和触控板，并遵循系统连击时间；自建时间窗口只作为其他平台与异常事件的回退。
- 回归测试必须覆盖“收到释放沿，但组合按钮状态仍为按下”的样本，而不能只测试理想化的释放状态。

## 悬浮窗目标校验

非激活悬浮窗在部分 macOS 版本上被点击后，`frontmostApplication` 仍可能短暂返回本应用。此时不能把 `activation_target == None` 直接解释为原输入目标丢失：应确认冻结窗口仍存在，并将粘贴或回车定向投递到该目标；只有明确检测到另一个外部窗口时才判定目标已变化。

## 连续触发的状态清理

- 完成后的快捷回车时间窗不能直接吞掉新的手势或连击；开始下一次手势流程时，应明确消费旧的回车动作。
- 悬浮球真正回到空闲态时，应同时清理晃动轨迹、连击序列和冷却时间，避免上一次会话的检测状态阻止下一次触发。
- 取消属于正常终止，不应复用错误状态或警告图标；错误反馈只用于真实失败。

## 全局监听自恢复

macOS 的 `CGEventTap` 可能在应用长期处于后台、系统切换输入状态或回调超时后被系统禁用。只在禁用事件回调里尝试恢复不够稳妥：监听线程还应定期检查 tap 是否启用，并在发现禁用时主动重新启用，避免必须先点击应用窗口才能继续识别。

## 不要用 `NSApp.currentEvent` 判断全局鼠标当前位置

`NSApp.currentEvent` 表示 AppKit 最近一次派发给应用的事件，并不保证事件仍在处理。悬浮球被点击后，如果把该事件的 `window` 当成实时命中结果，后续全局连击会一直被误判为发生在悬浮球上，直到应用收到另一条本地事件。异步或全局监听中的悬浮窗命中判断必须使用当前鼠标坐标与窗口边界计算。

## 原生改造后的 WebView 窗口只隐藏复用

悬浮球创建后会把 Tauri 的 `NSWindow` 运行时改造成 nonactivating panel。正常关闭功能时不要在事件循环中销毁这个仍被 Tao/WebView 持有的窗口，否则 Objective-C 异常可能跨过 Rust 边界导致整个应用中止。开关关闭时隐藏窗口并禁用命中；再次启用或临时手势触发时复用同一窗口，进程退出时再交给框架统一释放。

## 快捷回车的安全检查时机

文本自动注入成功，意味着注入前已经确认过目标不是安全输入框。点击非激活悬浮球后，macOS 可能暂时无法从该目标应用读取焦点控件；此时重复执行安全输入框探测会把 AX 读取失败误判成“不能发送回车”。只有当前前台窗口仍可明确匹配原目标时才重新探测；前台查询因悬浮球暂时返回空值时，复用注入前已经完成的安全检查。
