# 麦克风并发启动重复开流导致录音被成倍拉长

## 现象

音频调校试听「处理后」听起来像慢放：说 3 秒，录音文件 12～17 秒，音高基本不变。原始录音几乎没声音（峰值约 -46 dBFS）。重复进出页面后越来越慢。

## 排查

1. 读试听临时文件（`%TEMP%\say-it-audio-lab-*.wav`，应用占着时用 `cp` 复制出来再读）：采样率、时长自洽，排除写 WAV 用错采样率。
2. 用 Python `sounddevice` 走 WASAPI 直接录同一设备：每秒 44100 帧，排除设备和驱动问题。
3. 在 `capture_tests.rs` 里用 4 个线程同时调 `start_backend_mic_inner`：每秒收到 176128 个采样，正好 4 倍，复现成功。

## 根因

`start_backend_mic_inner` 先检查「worker 已在跑且设备相同」，再起新 worker。检查和起 worker 之间没有互斥，并发调用会各开一条 cpal 流：

- 每条流都往同一个 `BackendMicState` 推样本，消费者收到的音频按回调块（约 10ms）交错重复，听起来就是慢放，音高不变；
- `guard.worker` 只保留最后一个，其余 worker 再也停不掉，重复的流一直累积。

电平预览的启停命令改成 `#[tauri::command(async)]` 后，命令不再在主线程上排队执行，这个竞态就很容易触发了。听写、字幕、对比、调校都走同一个入口，同样受影响。

## 修法

`RuntimeState` 新增 `backend_mic_lifecycle` / `backend_system_audio_lifecycle` 两把锁，`start_*_inner` 与 `release_*_inner` 全程持有，启动和释放严格串行。回归测试见 `concurrent_starts_open_a_single_capture_stream`（真实设备，需 `SAYIT_ALLOW_MIC_LIFECYCLE=1` 和 `--ignored`）。

## 经验

- 把同步 Tauri 命令改成 `async` 或 `command(async)`，命令就不再在主线程上依次执行。先确认它碰到的「先检查后创建」状态有没有互斥。
- 声音听起来像慢放但音高不变，优先怀疑采样被重复写入，而不是采样率标错（采样率标错时音高也会跟着变）。
