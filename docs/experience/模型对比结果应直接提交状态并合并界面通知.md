# 模型对比结果应直接提交状态并合并界面通知

## 触发条件

模型对比原先和听写、字幕共同消费容量为 256 的广播。界面序列化或消费者变慢时，最终句子、任务完成、连接结束可能被覆盖；比较会停留在处理中，或文本缺句。旧处理函数还把查找所属会话与写入单元格拆为多次加锁，期间 reset 可以让旧事件改到新一轮同索引单元格。

## 改动边界

- 识别与转写生产者统一经过 `application/events::publish_backend_event`。属于当前模型对比的事件在一次 CompareRuntime 锁内提交；其余事件继续进入原广播，保持听写与字幕的交付路径。
- 逐句 final、错误与 ended 仍逐条处理，所有最终文本完整累计。`Notify` 只合并界面刷新，既不合并最终句子，也不排队保留完整临时结果。
- 原对比广播消费者替换为等待刷新通知。结束事件立即移除当前任务/会话登记，并遵守文件导出尚未完成时不能提前回到 idle 的限制。
- 文件识别在创建工作任务前登记业务接收方。比较和文件听写使用同一注册入口；业务拒绝接收时取消并回收任务登记，不启动识别。实时识别继续使用已完成的“准备、登记、启动”契约。
- 单元格复用显示文本和累计文本缓冲；快照只复制公开显示字段，不复制被 serde 跳过的内部累计字符串。完整文本仍保留在后端，不截断结果。

## 验证与测量范围

本地回归覆盖显示暂停时 1000 句 final 全量保留、状态收敛、错误后结束保持错误、旧会话和旧 epoch、导出期间不可提前结束、文件完成/失败释放登记、通知等待间隙更新，以及无关事件继续共享给其他订阅者。文件注册另测先登记取消入口与业务方，以及拒绝登记后的回收和迟到事件拒绝。

独立压力测试 `application::compare::delivery::tests::stalled_comparison_profile`：255 次 65540 字节文本更新加 ended，共 256 条，暂停消费后再恢复。旧分支冻结 Arc 广播的容量和载荷所有权，新分支使用实际路由入口；最终文本与 idle 状态相同。两分支共用当前状态归并逻辑，对比只衡量交付缓冲和状态更新，不包含网络、真实模型和窗口渲染，也没有量化界面合并刷新的额外收益。

复现入口为 `scripts/measure-audio-performance.mjs` 的 `comparison-delivery` 与 `comparison-delivery-legacy` 场景，使用发布配置测试程序，每轮独立进程。内存和耗时都应报告，不能只挑改善项。

2026-09-24，Windows x64 release，最终实现新旧交替各测三轮，中位数如下：

| 指标 | 原广播缓冲 | 直接提交状态 |
| --- | ---: | ---: |
| 测试进程私有提交峰值 | 20.1484 MiB | 3.9844 MiB |
| 这 256 条更新的总处理耗时 | 9.5806 ms | 15.5654 ms |

两者最终文本哈希均为 `c6fd10dd3b2a124d`。内存下降伴随此压力场景约 6 ms/批的耗时增加，不能声称 CPU 性能也改善；同步交付保证最终结果不因刷新积压丢失，消除较大载荷排队，故保留此取舍。正常窗口刷新收益、真实逐字延迟与多模型调度仍需继续测量。

初次按新旧各连续三轮测量也观察到耗时增加，复用文本缓冲后仍存在。不同轮次耗时波动明显；最终同程序交替采样避免只报告有利轮次。原始结果保留在忽略目录 `工作区/performance/comparison-delivery*-interleaved-*.json`，此前采样为 `comparison-delivery{,-legacy,-buffer,-buffer-legacy}.json`，均带测试程序 SHA256。

剩余边界：听写与字幕的 ASR 广播以及文件听写广播仍可能因消费者落后丢失，不代表整个事件链路已可靠。实际界面/OBS 和 macOS 运行未在本阶段验证；同步状态更新也将一部分原消费者计算移到了生产者线程，需要继续以真实长文本和多模型负载评估延迟。

最终发布配置 Rust 回归：708 项通过、0 失败、29 项专用测试默认忽略；性能用例另行执行。日志为 `工作区/performance/comparison-delivery-final-tests.log`。
