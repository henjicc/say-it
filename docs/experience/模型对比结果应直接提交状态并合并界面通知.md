# 模型对比结果应直接提交状态并合并界面通知

## 触发条件

模型对比原先和听写、字幕共同消费容量为 256 的广播。界面序列化或消费者变慢时，最终句子、任务完成、连接结束可能被覆盖；比较会停留在处理中，或文本缺句。旧处理函数还把查找所属会话与写入单元格拆为多次加锁，期间 reset 可以让旧事件改到新一轮同索引单元格。

## 改动边界

- 识别与转写生产者统一经过 `application/events::publish_backend_event`。属于当前模型对比的事件在一次 CompareRuntime 锁内提交；其余事件继续进入原广播，保持听写与字幕的交付路径。
- 逐句 final、错误与 ended 仍逐条处理，所有最终文本完整累计。`Notify` 只合并界面刷新，既不合并最终句子，也不排队保留完整临时结果。
- 原对比广播消费者替换为等待刷新通知。结束事件立即移除当前任务/会话登记，并遵守文件导出尚未完成时不能提前回到 idle 的限制。
- 文件识别在创建工作任务前登记业务接收方。比较和文件听写使用同一注册入口；业务拒绝接收时取消并回收任务登记，不启动识别。实时识别继续使用已完成的“准备、登记、启动”契约。
- 单元格复用显示文本和累计文本缓冲；快照只复制公开显示字段，不复制被 serde 跳过的内部累计字符串。完整文本仍保留在后端，不截断结果。

## 验证与测量范围

本地回归覆盖显示暂停时 1000 句 final 全量保留、状态收敛、错误后结束保持错误、旧会话和旧 epoch、导出期间不可提前结束、文件完成/失败释放登记、通知等待间隙更新，以及无关事件继续共享给其他订阅者。文件注册另测先登记取消入口与业务方，以及拒绝登记后的回收和迟到事件拒绝。

独立压力测试 `application::compare::delivery::tests::stalled_comparison_profile`：255 次 65540 字节文本更新加 ended，共 256 条，暂停消费后再恢复。旧分支冻结 Arc 广播的容量和载荷所有权，新分支使用实际路由入口；最终文本与 idle 状态相同。两分支共用当前状态归并逻辑，对比只衡量交付缓冲和状态更新，不包含网络、真实模型和窗口渲染，也没有量化界面合并刷新的额外收益。

复现入口为 `scripts/measure-audio-performance.mjs` 的 `comparison-delivery` 与 `comparison-delivery-legacy` 场景，使用发布配置测试程序，每轮独立进程。内存和耗时都应报告，不能只挑改善项。

2026-09-24，Windows x64 release，最终实现新旧交替各测三轮，中位数如下：

| 指标 | 原广播缓冲 | 直接提交状态 |
| --- | ---: | ---: |
| 测试进程私有提交峰值 | 20.1484 MiB | 3.9844 MiB |
| 这 256 条更新的总处理耗时 | 9.5806 ms | 15.5654 ms |

两者最终文本哈希均为 `c6fd10dd3b2a124d`。内存下降伴随此压力场景约 6 ms/批的耗时增加，不能声称 CPU 性能也改善；同步交付保证最终结果不因刷新积压丢失，消除较大载荷排队，故保留此取舍。正常窗口刷新收益、真实逐字延迟与多模型调度仍需继续测量。

初次按新旧各连续三轮测量也观察到耗时增加，复用文本缓冲后仍存在。不同轮次耗时波动明显；最终同程序交替采样避免只报告有利轮次。原始结果保留在忽略目录 `工作区/performance/comparison-delivery*-interleaved-*.json`，此前采样为 `comparison-delivery{,-legacy,-buffer,-buffer-legacy}.json`，均带测试程序 SHA256。

剩余边界：听写与字幕的 ASR 广播以及文件听写广播仍可能因消费者落后丢失，不代表整个事件链路已可靠。实际界面/OBS 和 macOS 运行未在本阶段验证；同步状态更新也将一部分原消费者计算移到了生产者线程，需要继续以真实长文本和多模型负载评估延迟。

最终发布配置 Rust 回归：708 项通过、0 失败、29 项专用测试默认忽略；性能用例另行执行。日志为 `工作区/performance/comparison-delivery-final-tests.log`。

## 完整应用的本地模型对比验收

`comparison-app-3` 使用独立应用标识、真实 Tauri 事件循环、正式模型对比命令和无网络权限的 API v5 插件。30 分钟 WAV 每次由两个文件模型实际读取，每个返回 2,000 句；连续三轮成功、非协作取消、主动失败、再次成功，结束后检查对比 idle、音频租约释放，以及通用转写缓存中没有对比子任务。最后混合文件模型与实时模型，按实际时钟投喂 5 秒音频，并严格验证实时模型收到的 160,000 字节。

本轮程序 SHA256 为 `E5421F6459F66C39617FC080233DFA2D30145202EBE51E2FD6716E9E1BF85425`。初始私有提交 6.63 MiB；三轮文件对比后的闲置为 19.23、20.08、23.03 MiB；混合对比后的最终闲置 28.68 MiB，19 线程、214 句柄；运行阶段观测峰值 46.66 MiB。结束后的采样区间 CPU 差分为零，不能推断所有时间绝对零 CPU。进程退出后无残留子进程。

堆统计中，三轮文件对比后的实际已分配量约 1.52、1.53、1.54 MiB；已提交量明显更高。不能仅看提交量推断完整文本泄漏，也不能据三轮结果宣称所有内存已经稳定。还需较长轮次和分配器对照。非协作插件取消到工作退出约 3.02 秒，对应既有析构预算，不是界面取消响应耗时。

这是应用级宿主生命周期验证，不是真实 ASR 质量测试。插件包含用于采样的固定四秒等待和本地分块读取，因此完成耗时不能用作识别速度基准；本轮无同条件旧应用基线，不报告整应用优化百分比。上文“剩余边界”描述当时阶段，听写随后已完成直接提交改造，详见听写相关经验。

## 空闲堆缓存回收对照

验收构建额外提供 `-OptimizeIdleHeap`，在每轮任务结束后调用 Windows `HeapSetInformation(NULL, HeapOptimizeResources, ...)`。这是系统堆管理器对空闲缓存的回收，非工作集修剪；不卸载活对象，不进入正式构建。[接口约定](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heapsetinformation)。

`comparison-heap-opt-1` 完整通过同样的三轮对比和混合模型验收，程序 SHA256 为 `73630B7C92FFA90396211FE24CD1767F9C62F1E2D5244F6B14BE652B0FBE0296`。同一进程每次回收前后相邻稳定阶段的私有提交为：11.31→8.41、13.66→9.31、14.14→10.03、22.73→10.24 MiB；各次调用耗时 0.82～1.24ms。退出后无残留子进程。任务结束后保留的完整比较文本仍按验收要求存在，后续任务照常成功。

不要只根据 `HeapSummary(GetProcessHeap())` 判断回收是否有效。本次默认堆统计有的轮次完全不变，但进程私有提交实际下降；该统计是辅助信息，不能替代完整进程采样，更不能把两种统计相减推断其他堆的精确大小。上述前后值来自约一秒间隔的进程采样，并非调用内部的瞬时测量。

后续正式采用前，需补上空闲状态触发、连续操作的合并和任务重启验证；不得在每个音频包或固定高频定时器上执行回收，也不能把这里的验收开关直接当成已经交付的产品优化。

## 自动回收的应用级对照

2026-09-25 补齐事件触发的正式实现：窗口销毁、识别/转写工作实际结束以及相关领域结束时合并通知，最后一次通知后等待五秒。回收前检查音频租约、识别与转写登记、听写、字幕、模型对比和音频调校状态；忙碌时跳过，由下一次释放通知重新触发。回收放在阻塞工作线程，没有永久轮询，不在音频包或界面线程上执行。检查是避免干扰的尽力判断，不是禁止任务启动的全局锁，因此只能调用系统线程安全的空闲堆回收，不能据此销毁活对象或卸载模型。

相同程序 SHA256 `48CA5D5FBF4F49F126BF86F314C0DA4B1124FFCEB8C5730473A83147FE56356A`，分别关闭/开启自动回收完成三轮文件模型对比及混合实时模型验收，均无手动回收。测量目录为 `工作区/performance/auto-reclaim-comparison-{off,on}`，每次 243 个采样点，退出后均无残留子进程。

| 私有提交 | 关闭自动回收 | 开启自动回收 |
| --- | ---: | ---: |
| 初始闲置 | 6.59 MiB | 6.57 MiB |
| 第一轮文件任务后 | 19.63 MiB | 8.64 MiB |
| 第二轮文件任务后 | 15.30 MiB | 9.46 MiB |
| 第三轮文件任务后 | 16.04 MiB | 10.18 MiB |
| 混合模型后的最终闲置 | 26.76 MiB | 10.23 MiB |

自动回收执行四次，忙碌跳过六次；关闭时两项计数均为零。两组最终均为 19 线程、214 句柄，最后一个约一秒采样区间 CPU 差分为零。约 62% 是本场景最终闲置提交量的差异，不能作为整个软件或所有工作负载的优化比例。插件有固定等待，任务总耗时不能用于评价 ASR 速度。单次完整对照证明机制有效，不能证明长期运行绝不增长。
