# 字幕翻译请求需要有界排队且取消后等待实际退出

## 原因

此前每个字幕分句都会直接启动异步翻译任务及对应 JavaScript 工作线程。插件请求最多可以等待两分钟；服务变慢时，完成译文的历史回收并不能限制尚未完成的请求数量。

## 调度与边界

- 每个字幕会话最多执行 8 个翻译请求，最多排队 256 个分句，排队原文总量最多 4 MiB。排队项只保存请求数据和配置快照，不创建等待信号量的后台任务或脚本线程。
- 分句按 FIFO 启动；流式结果仍按原有序号重组，供应商输入、识别结果和译文内容不进行截断或合并。
- 排队只冻结模型、语种和原文，不保存供应商执行对象；真正启动时重新解析并验证供应商，防止排队期间停用或卸载插件后仍使用旧权限执行。
- 一个请求已经失去所有字幕文档引用时，排队项直接释放，执行项收到独立的子取消令牌。执行项必须等底层调用退出后才释放名额，不能在发出取消信号时就启动替代请求。
- 退出守卫直接归还名额，不依赖广播最终事件是否及时被消费。守卫也覆盖异步任务被丢弃或异常退出；会话编号不匹配时不能修改新会话的队列。
- 停止或替换会话会取消执行项，释放排队数据；父取消不会启动剩余队列。分句沿用 ASR 事件所属于的 epoch，避免事件处理与入队之间切换会话后误归属。
- 关闭字幕翻译时同样清空排队项、取消执行项，但不取消原文字幕会话；未完成的文档占位也必须结算，因为取消请求不再发出 done，不能等待一个永远不会到达的完成事件。重新开启后可继续接收新分句。
- 队列满时通过既有字幕翻译错误投影明确报告“本段未能翻译”；原文字幕继续更新。不能宣称超载情况下也保证所有分句翻译成功，不隐藏失败或用无限等待换取表面成功。
- 单次已经获准直接执行的输入仍使用供应商原有输入限制；4 MiB 是排队文本预算，不是全进程内存预算。停止旧会话与启动新会话期间仍可能有清理工作短暂重叠，8 是单会话执行上限，不能宣传为全进程线程上限。

## 验证

2026-09-24 发布配置 Rust 回归：687 项通过，26 项忽略，无失败。新增验证：

- 填满 8 个执行位置和 256 个排队位置后拒绝额外请求；完成后按 FIFO 继续，所有获准请求保留。
- 排队字节上限独立于数量上限，执行与过期移除后预算准确归还。
- 取消过期请求不提前释放名额；重复退出不会归还其他请求的位置。
- 停止会话不启动排队任务；丢弃旧队列不取消新会话。
- 连续 1,000 次关闭翻译后，没有等待已取消请求的空占位累积，原文字幕取消令牌保持未取消。
- 弱引用证明过期排队项实际释放原文载荷。
- 264 个本地异步慢操作全部返回对应结果，并发峰值为 8，结束后执行与排队集合均为空。

新增测试不调用设备或真实供应商；它们证明调度容量、顺序和取消边界，不能代替真实服务吞吐、完整桌面交互、macOS 或整应用资源测量。上限选择需要后续根据实际负载继续校准；有界并发也意味着极端突发时会增加排队等待。
