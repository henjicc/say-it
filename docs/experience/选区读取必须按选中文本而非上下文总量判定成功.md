# 选区读取必须按选中文本而非上下文总量判定成功

## 问题

通用上下文读取会同时收集焦点文本、光标附近文本、可见文本和文档文本。如果选区专用流程复用“总文本量达到阈值即成功”的判定，焦点元素一旦返回足够多的正文，就会提前停止祖先查找。Chromium、Electron 和跨节点选区经常只在祖先的 UIA TextPattern / macOS AX 元素上暴露选中文本，因此最终会出现“能读到页面内容，但读不到选区”的假成功。

## 正确做法

- 选区模式只以非空 `selectedText` 判断读取器成功，不能使用通用上下文总量。
- 选区原文不能经过通用上下文的空白折叠；换行、缩进以及首尾空格都可能是编辑语义的一部分，只做空白选区判空和长度截断。
- Windows 依次尝试焦点元素 UIA、最多 10 层 UIA 祖先、IA2/MSAA、Win32 Edit/RichEdit，最后才使用受保护的剪贴板复制回退。
- Windows 剪贴板回退优先尝试 `Ctrl+Insert`，再回退 `Ctrl+C`；读取时等待剪贴板短暂稳定，兼容 PDF 等会分阶段写入多种格式的应用。
- UIA 祖先只调用 `GetSelection`，不要读取祖先 DocumentRange；后者可能把整篇 Chromium 文档误判为选区。
- macOS 在 `AXSelectedText` 缺失时使用 `AXValue + AXSelectedTextRange` 还原文本，并同时检查子节点和最多 10 层祖先。
- 非文本对象选区必须阻止模拟复制，避免对图片、树节点等执行无关的 Ctrl+C 行为。
- 剪贴板回退必须完整备份格式，并用 change-count/sequence 校验竞争；检测到用户并发修改时保留用户新内容，同时放弃本次选区结果。
- 能取得选区边界时将其纳入二次校验；允许少量辅助功能坐标抖动，但目标窗口、文本或明确边界发生变化时禁止覆盖。
