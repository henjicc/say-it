# 语音前端处理要用识别字错率评估：降噪反而降低识别率

## 结论

改动听写的音频前端（降噪、去混响、滤波、增益、重采样）时，用“识别字错率”判断好坏，不要凭耳朵。听起来更干净，不等于识别更准。

2026-11 一次远场模拟评估（FunASR Nano / SenseVoice，各 24 句）：

| 方案 | 远场 | 远场 + 噪声 | 极低电平 |
|---|---|---|---|
| RNNoise 100%（当时的默认） | 15.6% | 33.8% | 15.1% |
| 关闭降噪 | 4.9% | 9.6% | 4.9% |
| 关闭降噪 + 97 阶 FIR 抽取 | 4.4% | 8.2% | 5.1% |
| 先整体归一化再 RNNoise | 17.3% | 39.3% | 18.2% |
| GTCRN / DPDFNet（sherpa-onnx 流式降噪） | 7.8～10.4% | 13～23% | 7～12% |
| 降噪结果与原声 30%～50% 混合 | 约等于不降噪 | | |
| 离线 WPE 去混响（6 抽头） | 4.9% | 6.2% | 4.7% |
| 90Hz 高通 | 略差 | | |

- 识别模型本身用带噪数据训练过，单通道增强留下的失真比噪声更伤识别。
- RNNoise 对低电平输入尤其糟：远场 -46 dBFS 的语音会被当成噪声大量抑制，听起来“怪、像慢放”。
- WPE 在“远场 + 噪声”下有收益，但这是离线迭代版本，在线版本要另外实现，收益也需要用真实录音确认。

## 评估方法（可复用）

材料放在 `工作区/audio-eval/`（gitignore）：

1. `texts.txt`：参考文本。用 Windows System.Speech（`Microsoft Huihui Desktop`，48k 单声道）合成干净语音到 `clean/`。OneCore 语音（Kangkang、Yaoyao）在 System.Speech 里不可用。
2. `degrade.py`：模拟远场，包括混响（RT60 0.4～0.6s，低频衰减更慢）、粉红噪声加低频隆隆声、峰值压到 -40～-52 dBFS，输出 float32 WAV 到 `degraded/<条件>/`。
3. `eval_tests.rs.txt`：临时 Rust 测试。用法是复制到 `src-tauri/src/audio_dsp/eval_tests.rs`，并在 `audio_dsp.rs` 里加 `#[cfg(test)] mod eval_tests;`。每个方案的输出直接送 sherpa-onnx 离线识别器，按字计算 CER。
   - `EVAL_VARIANTS=a,b` 选择方案，`EVAL_MODEL=sensevoice-small` 切换模型（默认 `funasr-nano-ctc`），`EVAL_ONLY=f` 只跑某个前缀的文件，`EVAL_VERBOSE=1` 打印错句。
   - 运行：`npm run test:rust -- --bin say-it eval_far_field -- --ignored --nocapture`。debug 下 WPE、DPDFNet 很慢，记得放后台跑。
   - 用完删掉，不提交。

合成语音和合成噪声与真实情况仍有差距。结论有分歧时，用调校台录下的真实远场录音（`%TEMP%\say-it-audio-lab-*.wav`）替换 `degraded/` 再跑一遍。
