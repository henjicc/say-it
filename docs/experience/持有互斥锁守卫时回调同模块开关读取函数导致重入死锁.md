# 持有互斥锁守卫时回调"开关读取函数"导致重入死锁

## 现象

普通听写识别完成、走到注入阶段时整个任务卡死，之后所有依赖应用配置的功能
（再次听写、实时字幕、打开设置页快照）全部无响应，只能杀进程。

## 根因

`state.app_settings` 是 `std::sync::Mutex`（`prelude.rs` 导出的 `std::sync::Mutex`），
**非可重入**。`final_draft::observation_allowed` 用 let-else 把守卫绑定到局部变量并
持有到函数结束，随即在 `&&` 链里回调 `learning::observation_enabled(&state)`，
后者又 `state.app_settings.lock()`——同线程二次加锁直接自死锁，且该线程从此
永久持有这把锁。

```rust
// 错误写法
let Ok(settings) = state.app_settings.lock() else { return false };
let prefs = &settings.history_prefs;          // 守卫被 prefs 借用，活到函数结束
prefs.get("enabled")... != Some(false)
    && learning::observation_enabled(&state)   // ← 内部再次 lock()，死锁
```

两个放大因素让它很难被发现：

- **`&&` 短路救不了**：`history_prefs.enabled` 默认是 `true`，所以第一个操作数为真，
  第二个必被求值。死锁发生在读到真正的开关值之前。
- **锁被永久占住**：不只是当前任务挂死，而是此后每一条读 `app_settings` 的路径
  都跟着挂死，表象是"整个应用坏了"，很难回溯到某一个具体函数。

## 规避方式

**在已持有某把锁的上下文里需要再读同一份数据时，从手上的守卫直接读字段，
不要回调任何"自己也会加锁"的函数。**

把判定抽成只接受数据、不接触 `RuntimeState` 的纯函数：

```rust
// 纯函数：只读传入的 prefs，可安全地在持锁时调用
fn observation_allowed_for(prefs: &serde_json::Value, identity: &AppIdentity) -> bool {
    prefs.get("enabled").and_then(Value::as_bool) != Some(false)
        && prefs.get("finalDraftObservationEnabled").and_then(Value::as_bool) == Some(true)
        && !excluded(prefs, identity)
}

fn observation_allowed(app: &AppHandle, identity: &AppIdentity) -> bool {
    let Ok(settings) = app.state::<RuntimeState>().app_settings.lock() else {
        return false;
    };
    observation_allowed_for(&settings.history_prefs, identity)
}
```

这样同一个开关只剩一个读取实现，也不会出现前后端/两处实现判定漂移。

## 回归防线

纯函数本身不足以阻止后人把它改回去，配一条**限时接收**的契约测试：

```rust
#[test]
fn observation_allowed_for_is_safe_while_holding_app_settings() {
    let (tx, rx) = std::sync::mpsc::channel();
    std::thread::spawn(move || {
        let state = RuntimeState::default();
        let settings = state.app_settings.lock().unwrap();
        let allowed = observation_allowed_for(&settings.history_prefs, &identity);
        drop(settings);
        let _ = tx.send(allowed);
    });
    if rx.recv_timeout(Duration::from_secs(3)).is_err() {
        panic!("持有 app_settings 守卫时调用已阻塞");
    }
}
```

注意**不能直接 `#[test]` 调用会死锁的代码**——那样 `cargo test` 会挂住而不是失败。
必须放到独立线程里用 `recv_timeout` 判定。

## 排查与检查清单

写新代码或 review 时，只要看到"持锁 → 调用另一个函数"，就要追进被调函数确认它不加同一把锁。
本仓库 `learning.rs` 里的 `learning_enabled` / `cloud_context_enabled` 是同类高危函数，
已在其上方加了警示注释。

同类问题此前已出现过一次（见
`Rust变量遮蔽不释放互斥锁导致智能处理死锁.md`），根因同为"守卫比预期活得久"。
两次的差别在于：那次是变量遮蔽导致守卫没被 drop，这次是守卫被借用而合法存活到函数结束。
**共同的检查点是"这一行执行时，哪些锁还被我持有"，而不是"我有没有显式 drop"。**
