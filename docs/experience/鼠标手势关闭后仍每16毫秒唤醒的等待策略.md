# 鼠标手势关闭后仍每 16 毫秒唤醒的等待策略

## 根因

识别线程启动后始终用 `recv_timeout(16ms)` 检查消息。关闭手势只让每轮提前返回，线程仍反复醒来并读取配置。启用后无鼠标输入时，同样每秒检查约 60 次；真正需要定时执行的只有 140ms 停顿判定和一秒监听健康检查。

## 处理边界

- 将配置变化与重置也放入同一个消息通道。关闭时使用没有截止时间的接收；启用、关闭、参数修改、监听启动失败、保存失败回退和会话结束重置都必须通知，不能只修改共享状态。
- 启用时等待最早的实际停顿期限与健康检查期限，鼠标事件仍立即唤醒。每次有效移动更新停顿时间；不足三个样本、判定结束、拖动和重置之后不能留下已过期的停顿期限，否则会变成忙循环。
- 保留一秒监听健康检查，尤其不能取消 macOS 全局监听被系统禁用后的恢复路径。关闭期间不做健康检查，再次启用时允许立即检查。
- 每次收到事件后读取当前配置，不为计算下次等待额外读取一次。配置更新后的通知覆盖“线程刚读取旧配置就开始等待”的竞态。
- 没有改动原始鼠标按钮边沿、连击次数、拖动排除、灵敏度阈值与冷却规则。停顿到点即可判定，不再附加最长一轮固定检查延迟。

## 验证与限制

手势相关 21 项测试通过，完整 Rust release 回归 661 项通过、23 项显式忽略、0 项失败。新增测试覆盖关闭时无限等待、配置与鼠标消息唤醒、通道关闭退出、停顿随移动续期、判定与重置后取消期限、健康检查优先以及短序列不会忙循环；原有 Windows 输入包和 macOS 释放沿领域回归继续通过。

Windows release，每场景三个独立进程，取中位数。在两秒无鼠标输入后发送控制消息结束等待，对比冻结的旧 16ms 检查与新等待策略：

| 场景 | 旧等待返回次数 | 新等待返回次数 | 旧线程 cycles | 新线程 cycles |
| --- | ---: | ---: | ---: | ---: |
| 关闭手势 | 121 | 1 | 9,159,276 | 87,431 |
| 启用但无输入 | 121 | 2 | 9,053,234 | 238,650 |

线程 cycles 分别下降约 99.0% 和 97.4%。关闭场景唯一一次返回来自结束测量的控制消息，并非定时唤醒。进程峰值私有提交均约 3.8 MiB，没有明显内存收益；不能将这些数字当作整应用 CPU、操作系统总上下文切换或功耗降幅。

测试不安装全局监听、不移动鼠标、不触发真实听写。未进行物理鼠标交互和 macOS 实机验收，领域测试不能替代这些证据。可重复入口是 `scripts/measure-audio-performance.mjs` 的 `gesture-idle[-legacy]` 与 `gesture-enabled-idle[-legacy]`；原始 JSON 在工作区/performance/gesture-scheduling-*.json，含程序 SHA256。
