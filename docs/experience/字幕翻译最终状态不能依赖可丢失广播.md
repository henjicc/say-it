# 字幕翻译最终状态不能依赖可丢失广播

## 触发条件与根因

字幕流式翻译曾将完整临时译文与最终结果都发送到容量为 256 的共享广播。字幕消费者落后会收到 `Lagged` 并跳过事件；若被覆盖的是最终结果，文档无法记录完成状态，稳定历史回收也可能延后。即使使用 Arc 共享载荷，暂停消费时仍可能保留 256 份较大的临时译文；听写和模型对比还会被无关翻译事件唤醒。

## 正确边界

- 翻译回调直接在字幕 Session 锁内提交结果、错误和完成状态；保留 epoch、序号、会话阶段和已完成检查。
- 提交后只发送 `Notify::notify_one()`，表示显示需要刷新。通知可以合并，最终业务状态不可丢失；不增加无限队列或逐更新任务。
- 刷新仍由原字幕事件循环执行。公平 `select!` 同时等待识别事件与翻译通知，避免持续翻译更新压住识别处理。
- 输入按借用传递，仅复制显示所需尾部；遵守已有 1800 字符展示与 1801 字符内部保留规则。临时文本可能缩短，不能用它提前删除旧结果。
- 翻译队列仍在实际工作退出后释放并发名额，取消与停用仍沿用已有策略。状态提交失败记录诊断。

这一修改只解决翻译交付。ASR 与转写事件仍使用有限广播，其关键状态交付需要独立检查，不能声称整个事件系统已经可靠。

## 验证与复现

`subtitles/delivery_tests.rs` 覆盖 1000 次更新和共享广播积压、最终结果缩短、乱序完成、失败保留部分译文、旧会话/未知序号/停止后回调、待处理通知跨会话、4000 次完成和空结果回收，以及刷新期间更新不丢通知。现有保留策略测试继续对照旧显示输出，包括 Unicode 和空白边界。

性能测试 `stalled_renderer_profile` 用本地字符串模拟显示消费者暂停：512 次更新，临时文本为 65540 字节，最后一次为短最终结果。旧分支重现容量 256 的 Arc 广播，新分支直接提交状态；两者最终显示相同。它测的是翻译交付缓冲，不包含网络、真实供应商、音频、OBS 或窗口渲染；不能把结果当作整机节省量或真实字幕延迟。

复现入口为 `scripts/measure-audio-performance.mjs`，场景 `subtitle-delivery` 与 `subtitle-delivery-legacy`，使用 `scripts/run-rust-tests.mjs --release --no-run` 生成的测试程序，每轮独立进程。

2026-09-24，Windows x64 release，同一测试程序分别执行 3 次：

| 指标（三次中位数） | 旧广播交付 | 直接状态交付 |
| --- | ---: | ---: |
| 测试进程私有提交峰值 | 20.1289 MiB | 3.7695 MiB |
| 提交并消费这批更新的耗时 | 10.1774 ms | 0.7020 ms |

旧分支暂停后只剩最后 256 条可消费，新分支已提交全部 512 次更新；两者最终文本均为“最终完整译文”。这是合并临时更新、避免完整载荷排队的压力对照，数值不能外推到正常联网时的逐字延迟。

结果保存在忽略目录 `工作区/performance/subtitle-delivery{,-legacy}.json`，记录测试程序 SHA256。发布配置 Rust 回归 694 项通过、0 失败、28 项专用测试默认忽略；本次性能用例另行执行。真实窗口、OBS 与其他平台未在这一阶段完成端到端验证。
