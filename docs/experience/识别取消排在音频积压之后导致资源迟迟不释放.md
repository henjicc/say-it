# 识别取消排在音频积压之后导致资源迟迟不释放

## 根因

识别会话原先将 `RawF32`、`Finish`、`Stop` 放进同一个无界 FIFO。取消虽然把会话从全局表移除，却只向队尾追加 Stop，工作线程仍会依次执行全部积压音频的 DSP、模型推理或网络发送，再释放模型和缓冲。SDK 与 JavaScript 插件运行时另外创建的取消位没有接到会话的取消操作，阻塞的初始化或请求也无法及时中断。

## 实现边界

`asr_input` 统一管理识别接收端及独立取消信号。`AsrStreamHandle::stop` 先设置共享取消位，再唤醒异步等待和空队列上的接收者。接收前后均检查取消；一旦观察到取消，直接销毁接收端与积压 PCM，只向消费者交付 Stop。已持有旧 sender 的采集端随后收到关闭错误。

SDK/插件宿主使用同一个取消位，中断正在等待的 JavaScript promise、HTTP/WS 等操作，并沿用已有宿主清理和插件 dispose 机制。本地模型在初始化前后检查取消，当前推理返回后不再发布已取消结果。Apple 路径同时让取消打断阻塞的音频写入，并执行现有助手进程清理。

必须区分正常结束与取消：Finish 仍留在音频队尾，保证完整处理尾音。只有明确取消的任务才跳过剩余音频，不能拿此机制当作运行中队列超限时的静默丢包策略。共享取消状态只属于当前会话，不能复用于新会话。

## 验证与实测

Windows 发布配置，5 分钟合成 48 kHz 单声道音频提前排队，启用真实 DSP 降噪，随后取消；旧 FIFO 与新接收端各运行三个独立进程，取中位数。没有加载 ASR 模型或使用真实供应商服务。

| 指标 | 旧 FIFO | 独立取消 |
| --- | ---: | ---: |
| 取消至消费循环结束 | 1122.20 ms | 4.33 ms |
| 消费者首次取消息后的私有提交 | 61.68 MiB | 4.40 MiB |
| 完整退出后的私有提交 | 4.19 MiB | 4.14 MiB |
| 取消后仍处理的样本数 | 14400000 | 0 |

两种方案的取消前峰值都约为 61.7 MiB。本次改善的是取消后的停止和回收速度，并未降低正在运行的无界队列峰值；不能把测试耗时作为包含模型推理及销毁成本的完整应用取消延迟。

回归覆盖正常 Finish 音频顺序与全部尾部样本、带积压时优先取消、重复取消、旧 sender 关闭、会话隔离、阻塞/异步接收唤醒、已进入 Pending 的写入与取消等待、实际 stop 命令入口。现有本地 HTTP 停滞测试改为通过真实 ASR 句柄触发取消，并在积压未消费时验证 JavaScript 宿主请求中断及资源计数归零。完整发布配置回归：589 项通过、12 项性能测试显式忽略、0 项失败。

复现：`node scripts/run-rust-tests.mjs --release --no-run` 后，使用 `scripts/measure-audio-performance.mjs --scenario asr-cancel --executable <测试二进制> --output <结果.json> --seconds 300 --runs 3`。旧 FIFO 使用 `--scenario asr-cancel-legacy`。报告保存二进制 SHA256、回收阶段内存和取消后的处理样本数。

## 剩余限制

- 不可中断的本地模型创建/单次原生推理仍需等当前调用返回；本次不声称强制中断底层推理。
- 模型销毁、插件 dispose 和操作系统分配器回收有各自成本，不能只看会话从映射表删除就认定全部资源已释放。
- 输入队列仍无容量上限，后续需独立建立预算和背压/存储策略。
- Apple 的共用异步取消机制已用本地管道测试；macOS 助手及原生识别未进行运行时实测。
