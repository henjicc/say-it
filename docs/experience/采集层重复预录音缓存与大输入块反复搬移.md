# 采集层重复预录音缓存与大输入块反复搬移

## 问题

`push_backend_mic_samples` 将每个完整音频块发给原始消费者后，只要没有直接 ASR 通道，就继续放进 `pending`，最多 240 × 4096 个 f32 样本（3.75 MiB）。预录音对实时听写、字幕的静音重连有用，但文件听写、音频调校和录音模型对比已经直接收到全部样本，不会从这里重新绑定识别，因此是重复保留。

采集分包原来先追加整个设备输入，再反复从 Vec 头部 drain 4096 帧，每次搬移剩余数据。大块输入会产生随块数增长的重复搬移，buffer 容量还会长期保留峰值。

## 改动与约束

- 每个原始消费者显式声明 `AsrPreroll`。实时听写和字幕启用；文件听写、音频调校和模型对比禁用。模型对比的迟到消费者补发由对比运行时自己负责，不经过直接 ASR 绑定。
- 关闭的消费者及时移除；没有需要重连的消费者时释放预录音。保留原来的 240 块历史范围，不改变静音重连的音频顺序或时长。
- 只填满当前 4096 帧缓冲，再转移给下游，拼包 buffer 容量最多 4096 个 f32（16 KiB），不随输入块大小增长。
- 没有直接 ASR 和预录音需求时，原分配交给最后一个原始消费者；多个消费者仍收到内容相同的独立数据。直接 ASR 发送失败时从发送错误取回原分配，继续保留必要的重连开头。
- 尾包仍在暂停时排空；预录音只补给直接 ASR，不重复发给已经消费过它的原始监听器。

## Windows 发布配置测试

旧采集逻辑冻结在测试代码中，对照新生产采集入口。48 kHz 单声道合成音频，各组三个独立进程取中位数。480 样本是 10 ms 回调量；480000 样本是用于检测大块搬移的压力输入，不能视作常规设备行为。计时包括生成输入、采集分包、队列读取和输出哈希，不打开设备、不运行模型、不写音频文件。

| 音频时长 / 输入块 | 原峰值私有提交 | 新峰值私有提交 | 原处理耗时 | 新处理耗时 |
| --- | ---: | ---: | ---: | ---: |
| 5 秒 / 480 | 4.73 MiB | 3.72 MiB | 1.31 ms | 0.95 ms |
| 5 分钟 / 480 | 8.13 MiB | 3.95 MiB | 44.34 ms | 40.79 ms |
| 30 分钟 / 480 | 8.13 MiB | 3.96 MiB | 255.90 ms | 219.74 ms |
| 5 分钟 / 480000 | 15.27 MiB | 8.39 MiB | 205.86 ms | 64.76 ms |

纯录音消费者的重复预录音由最多 983040 个样本降为零。旧拼包 buffer 在常规输入下容量为 7680，大包压力输入下为 960000；新路径均为 4096。输出哈希逐项相同：5 秒 `5f674646be03cc62`、5 分钟 `f9c0d1d7d63e9fb9`、30 分钟 `27f0716cce6ac7a5`。这些是采集组件的进程测试数据，不代表整个应用的内存或端到端识别速度。

新增回归对照 1、479、480、4096、4097、480000 样本分包，验证输出、尾包、拼包容量、多消费者数据和最后分配转移、闭合监听器退出、240 块重连历史与实时尾包顺序、直接通道失败后的开头保留。完整 Rust release 回归：600 项通过、15 项性能测试显式忽略、0 项失败。

复现：构建 release 测试程序，使用 `scripts/measure-audio-performance.mjs --scenario capture --executable <测试程序> --output <结果.json> --seconds 1800 --packet-size 480 --runs 3`，旧路径为 `capture-legacy`。结果记录测试程序 SHA256、峰值与阶段内存、耗时、输出哈希、保留样本和拼包容量。

## 剩余范围

消费者通道仍是无界队列；本次只限制拼包缓存并消除无用途的重复历史，不能声称慢消费者积压已解决。系统音频与麦克风共用分包实现；macOS 已同步更新字段使用，但未进行 macOS 运行时或实际设备验证。
