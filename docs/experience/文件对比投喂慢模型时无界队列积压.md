# 文件对比投喂慢模型时无界队列积压

## 问题与范围

上传文件模型对比虽然已改成有界解码（两份 1600 样本包），下游仍以无界通道投喂实时模型。模型初始化、原生推理或网络处理慢于输入时，解码端有界并不意味着整条投喂路径有界：音频会继续堆在识别输入队列。

文件是可重读输入，可以等待消费者。本轮新增 `AsrInputSender`，集中计费队列内 Vec 分配容量与消息包装大小。文件投喂使用 `send_paced`，通过原子预留把排队计费预算限制为 64 KiB（约一秒 16 kHz 单声道 f32）。当前每包 1600 样本，最多同时排入十包，计费量为 64400 字节。消费者取走消息、队列销毁或发送失败时自动归还预算。已出队的处理包、发送方正在等待的一包、解码器预读包和通道自身元数据不在此计费数字里，因此它不是整个进程的内存上限。

投喂等待会向上游传播到有界解码器，按最慢的参与模型推进；仍保留原来每包至少 100 ms 的播放节奏。所有模型的采样内容、先后顺序和尾包不变，不增加缓存音频文件。

## 并发与取消约束

- 等待预算之前先登记 Notify，再检查预算和取消，避免释放通知落在检查与等待之间而丢失。
- 不在持有 ASR 会话表锁时 await；否则取消和会话退出可能被等待方阻塞。
- 取消使用已有独立标记，同时唤醒所有预算等待者，不需要等待原生识别调用返回。接收器退出也会唤醒发送方。
- 未完成的发送 future 被放弃不会占用预算；发送到已关闭队列会退还已预留计费。
- 计费使用 `Vec.capacity()`，不能只看逻辑长度；超过整个预算的单包立即返回失败，避免永久等待。生产文件输入由有界解码器固定为最多 1600 样本。
- 结束标记仍按 FIFO 排在全部音频之后；取消仍优先于积压。

设备回调不可等待，因此实时采集仍使用不等待的 `send`。它也进入统一计费，但没有在本轮被限制容量，不能把文件路径的预算称作全部 ASR 队列都已受限。它与原始采集消费者队列仍是后续重点。

## Windows 发布配置证据

合成 16 kHz 单声道 f32、1600 样本分包，快速注入；旧通道和新生产通道的本地消费者都先停顿 200 ms，再完整消费。每组三个独立进程取中位数，不运行模型、网络或真实设备。该压力测试刻意放大积压，不等于实际应用每 100 ms 投喂时的端到端表现。

| 音频长度 | 原峰值私有提交 | 新峰值私有提交 | 原总耗时 | 新总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 5 秒 | 4.18 MiB | 3.81 MiB | 200.83 ms | 200.75 ms |
| 5 分钟 | 23.06 MiB | 4.01 MiB | 206.93 ms | 206.70 ms |
| 30 分钟 | 119.06 MiB | 3.95 MiB | 237.85 ms | 237.22 ms |

总耗时包含统一设置的 200 ms 消费停顿，差异不足以宣称吞吐提速。30 分钟输入的生产方入队耗时从 56.37 ms 增至 237.09 ms：新增等待正是限制积压的机制，不能将入队完成当作识别完成。新路径各组最大观测排队计费均为 64400 字节；没有新增音频磁盘读写。

输出哈希完全一致：5 秒 `56b7df03790d608d`、5 分钟 `0125fb6df7831eb0`、30 分钟 `1b2e3ea68c5a2098`。另外复跑原取消压力场景（300 秒 48 kHz 输入积压），取消后处理样本数仍为零，取消及积压释放耗时中位数 4.57 ms。

回归覆盖并发生产者共享预算、等待后继续发送与尾包顺序、取消同时唤醒多个发送方、接收器失败、放弃等待、预分配容量、过大单包与已有同步积压。完整 Rust release 回归：606 项通过、16 项性能测试显式忽略、0 项失败。macOS 运行时未验证。

复现：构建 release 测试程序，执行 `scripts/measure-audio-performance.mjs --scenario asr-paced --executable <测试程序> --output <结果.json> --seconds 1800 --runs 3`；旧基线为 `asr-paced-legacy`。结果包括程序 SHA256、耗时、峰值与释放后内存、输出哈希及实际排队计费。
