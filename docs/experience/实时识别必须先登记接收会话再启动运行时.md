# 实时识别必须先登记接收会话再启动运行时

## 问题与影响

实时识别的四条后端路径原先在返回 session ID 前创建线程或异步任务。听写、字幕、模型对比在返回后才登记该 ID，模型对比还需要回放准备期间的音频。初始化立即失败或识别快速返回时，业务消费者可能先收到事件，再因 session ID 尚未登记而忽略它。广播是否积压与这个启动竞态是两个独立问题。

同时，调用方尚未确认连接是否属于当前会话，后台就可能开始创建 QuickJS、加载本地识别模型或启动平台助手。准备期间取消或业务登记失败时，这部分资源投入没有用途。

## 实现边界

`prepare_asr_stream_inner` 返回 `PreparedAsrStream`：音频入口已进入流表，但工作线程/任务的创建保存在一次性启动闭包中。听写、字幕先接入音频并登记 session ID；模型对比先回放开头音频并登记实时路由，然后消费准备对象调用 `start()`。

- 运行时、模型和平台识别会话在 `start()` 后创建，初始化产生的第一条事件已有业务接收者。
- 丢弃准备对象会移除流表登记、停止入口，并释放闭包捕获的音频接收器与资源，不创建额外等待线程或轮询任务。
- 启动失败走同一清理路径；成功启动后仍由原会话结束逻辑负责回收。
- 激活前再次检查入口是否已经关闭。运行中的取消仍由原接收器取消机制处理，不能宣称重型同步初始化随时可以中断。
- 字幕在音频接入前后都检查 epoch、活动阶段和是否已有连接，停止、失败和新会话不接收迟到准备结果。
- 浏览器凭据刷新、macOS 能力检查与资源准备仍可能发生在 prepare 阶段；这些不等于识别工作线程已经启动。

## 验证与取舍

`commands/asr/startup/tests.rs` 使用真实音频入口和本地启动闭包验证：立即事件晚于接收方登记、1000 次放弃准备均不执行初始化且释放登记与捕获对象、线程创建失败只取消本连接、激活前取消不初始化，以及音频包和 Finish 顺序。字幕补充所有会话阶段、旧 epoch 和已有连接的接入判定。

这个修复避免无效初始化，并修正启动事件归属；没有测量真实模型加载的内存降幅，不以模拟闭包推断整机性能。模型对比的初始化现在晚于开头音频回放，仍使用原来的有界音频暂存；极长准备积压下，首个模型初始化会相应推后，需要后续真实工作负载测量。

Windows 执行发布配置测试；macOS 分支仅同步修改了启动契约，尚未在 macOS 运行验证。ASR 与转写广播的消费者落后丢失风险仍需另行处理，不能用此修复代表整个交付链路已可靠。

2026-09-24 验证：启动专项 5 项通过，完整发布配置 Rust 回归 700 项通过、0 失败、28 项专用测试默认忽略。日志位于忽略目录 `工作区/performance/asr-startup-{target,full}-tests.log`。本轮没有调用真实识别或翻译服务，也没有完成实际窗口交互验证。
