# 字幕预览仍走 WebView 旧通道导致原生窗口不显示

## 根因与修复

正式字幕已使用 Rust 原生显示通道，但设置页的预览仍在前端计算布局、发送 WebView 专属配置事件。预览还先调用同步的 `get_indicator_monitor_metrics`；该命令会创建旧 WebView，在 Windows 同步 IPC 中按需创建 WebView 存在阻塞风险，原生字幕也收不到配置。

预览应使用异步领域命令，并复用正式字幕的显示器测量、尺寸计算、样式与原生/WebView 路由。演示文本和播放任务由 Rust 管理，独立于识别会话，不占用麦克风、不验证或调用供应商，也不向 OBS 写演示内容。前端只发送配置并投影 `previewActive`，让窗口关闭、页面离开和正式运行都能取消同一个任务。

WebView 回退首次创建时仍需在事件订阅就绪后重投影，重投影必须包含当前预览，不能仅检查真实识别会话是否运行。

## 连续开关的动画边界

验证中发现：窗口完全显示时 `Hide` 把动画方向设为退场；若首帧尚未推进就收到 `Show`，进度仍为 1。原来的 `Show` 只处理进度小于 1 的分支，旧退场方向会把新窗口再次隐藏。显示请求在进度为 1 时也必须取消退场方向。

## 验证方式

- 回归测试覆盖预览文本循环、双语滚动历史、单句替换、仅译文与取消任务；动画覆盖 `Hide → Show` 之间没有时钟推进的边界。
- 必须从实际预览领域命令验证到窗口，不能只直接调用底层文本绘制命令，否则会漏掉入口路由问题。
- 使用内置文本和不存在的模型 ID 即可验证翻译展示；运行快照应保持 `phase=idle`、`sessionId=null`、`obsOutputActive=false`。
- 原生窗口用 PIL ImageGrab 检查物理像素；`SAYIT_NATIVE_SUBTITLE=0` 检查首次创建和再次打开。鼠标点击、悬停、拖拽交由用户验证。
