# 听写识别结果直接入状态且终态动作只能领取一次

## 问题

听写原先从容量 256 的共享广播依次取结果，再等待 finalize 完成历史保存、上下文/模型处理与文字输出。消费者变慢时，新识别结果和结束事件可能被覆盖。扩大通道只能推迟问题，还会保留更多大段临时文本。

听写不能直接把所有副作用搬到识别生产者上：润色、历史、注入、取消和失败清理必须继续遵守原操作锁和执行顺序。

## 实现边界

- 实时和文件识别事件经过现有 Rust 路由，直接在听写 Session 锁内更新原文。每句 final 仍逐条累计，不截断完整结果。
- 每个 Session 只保留一个 `DeliveryState`：首个有效识别终态及是否已经领取。临时显示用 Notify 合并刷新，不排队保留完整文本，不按事件创建任务。
- 独立消费者领取一次终态，仍调用原 finalize/fail。历史保存、润色、原文回退、文字输出与资源回收保持原实现；旧处理期间新 Session 的结果仍能直接提交。
- 已收到失败时，`claim_injection` 拒绝收尾计时器提前取得输出资格。领取错误动作不会清掉这个标记；已失败不能因为消费了通知又被当成成功。
- 正常完成先到时，后续重复 finish/ended、迟到错误和文本不再改变已冻结结果。录音中意外 closed/ended 仍是失败；录音中的 finish 不会自行触发输出。
- 错误时保留 ASR ID，交给原失败清理停止连接。取消时清除投递状态，新 Session 默认重新初始化；动作携带 epoch，旧动作不能输出新会话。
- 临时文本复用缓冲；后台文字输出及原文保存只在消费终态后发生，没有放入识别回调。

## 本地验证

测试覆盖暂停消费时 1000 句最终文本完整保留、仅一次结束动作、失败与超时输出竞争、文件最终结果冻结、文件失败、录音中意外断开、无效阶段/旧连接、旧处理尚未完成时替换会话并交付新结果。既有 `claim_injection` 和后处理取消测试继续回归。

性能用例 `stalled_dictation_profile` 对照旧容量 256 的 Arc 广播与实际新路由。255 次临时/最终文本更新加 finish，暂停后恢复消费，校验原文和唯一 Finalize 动作；分别使用 126 字节和 65540 字节文本。两分支共用当前原文合并逻辑，不包含真实识别、网络、历史磁盘写入、润色或向其他软件输出。

使用 `scripts/measure-audio-performance.mjs` 的 `dictation-delivery{,-legacy}` 与 `dictation-small-delivery{,-legacy}` 场景，每次独立进程。数据只表示交付缓冲的局部收益，不能当作整机内存降幅或实际文字输出延迟。

仍需处理：字幕 ASR 目前还依赖广播；真实长会话、窗口/OBS、跨平台端到端和实际输出交互未在本阶段验证。

## 2026-09-24 测量结果

同一个 Release 测试程序、每组独立进程、交替运行三轮。256 个事件的中位数如下：

| 文本大小 | 旧广播峰值私有内存 | 直接提交峰值私有内存 | 旧耗时 | 新耗时 |
| --- | --- | --- | --- | --- |
| 65540 字节 | 20.180 MiB | 3.961 MiB | 8.917 ms | 12.292 ms |
| 126 字节 | 3.906 MiB | 3.797 MiB | 0.372 ms | 0.140 ms |

大文本积压场景减少约 80.4% 峰值私有内存，但这一整批同步交付耗时增加约 3.4 ms；保留该取舍的依据是完整结果不会因消费者落后而丢失，并消除了大文本队列滞留。小文本场景时间与内存均降低。两组对照的最终文本哈希各自完全一致。以上不代表实际听写端到端耗时。

全量 Release 回归：715 项通过、0 失败、30 项独立性能用例默认忽略。原始测量在忽略目录 `工作区/performance/dictation-*-interleaved-*.json`，记录测试程序 SHA256。
